# lib/features/onboarding/

Presentation-only — no `data/` or `domain/` layer, since onboarding has no data dependency (per the "a feature only has the layers it needs" rule in root `CLAUDE.md`).

```
presentation/
  onboarding_entry_gate.dart
                # OnboardingEntryGate — what route '/' actually builds; decides
                # whether onboarding is shown at all, from the session
  providers/    # OnboardingController — shared page-index state, 3 pages
  screens/      # OnboardingPageViewScreen — single PageView-based screen hosting
                # all 3 onboarding pages, swipeable, with a shared header/footer
  widgets/      # shared chrome (header, footer, progress indicator, primary button)
                # + one *_page_content.dart per page (first/authenticate/limit_stock)
```

- `OnboardingPageViewScreen` owns a `PageController`; the progress indicator and footer both key off it directly (via `AnimatedBuilder`) rather than piping per-frame scroll position through Riverpod state, which would fan out rebuilds.
- The "Next" button's default label (`AppStrings.onboardingNextButton`) is shared across `OnboardingFooter`, `OnboardingPrimaryButton`, and the explicit pass on the last page (which swaps to `onboardingGetStartedButton`) — don't reintroduce a separate hardcoded "ถัดไป" literal anywhere in this feature; reuse the constant.
- Onboarding's final screen hands off via `AuthGate` (from `features/auth/`) — see that feature's `CLAUDE.md` for what happens next.
- **`/` builds `OnboardingEntryGate`, not `OnboardingPageViewScreen`.** The gate watches `sessionProvider` (the one `features/auth/` owns) and only builds the screen when nobody is signed in; a restored session goes straight to `/home` and never renders a frame of the intro, and `loading` shows `AppLoadingScreen` for the same reason. `error` — offline, `/auth/me` down — lands on onboarding rather than a spinner, and shows nothing about the failure: the session error still reaches the user at `/home` through `AuthGate`'s `authErrorDisplayFor`, and a second error surface here would be a second door for the same message (ADR-0017/INF-20). All four branches are ADR-0023 D4 — read the class doc comment before changing any of them; it is the one place the reasoning lives, including what reopening the "route-level `redirect`" question costs.
- **The gate waits 2 s for the session and then stops waiting** (`OnboardingEntryGate.sessionDeadline`, ADR-0023 D8). It exists because a user with a stored token and dead wi-fi otherwise watched a spinner for as long as Dio took to give up (10 s `connectTimeout`) — the exact "can't open the app" failure D4 is about, arriving by another road. 🔴 **It is this gate's deadline, not an app timeout policy** (D8.1): don't "align" it with the Dio timeouts in `core/network/api_client.dart`, and don't hoist it somewhere shared — INF-05 absorbs it if a global policy is ever decided. 🔴 **Nothing on the deadline path cancels the restore or clears the session** (D8.2): a token that validates late is still honoured by `AuthGate` at `/home`, so the user pays by seeing the intro again, never by being logged out. Once the deadline has passed the gate latches on onboarding and a late session does **not** yank the reader out of the page they are on.
- **"Has this user already seen onboarding?" is derived from the session and stored nowhere** (ADR-0023 D1/D2). Signing out therefore brings the intro back on the next launch — that is the decision, not a bug, and `onboarding_session_entry_test.dart` locks it. Don't add a "seen onboarding" flag to close what looks like a gap; that needs its own ADR.
- **Page 2 has diverged from its Figma frame on purpose.** The frame (node 7:2) is titled "100% Authenticated Originals" and puts a "ยืนยันแล้ว" label under the centrepiece icon; both are gone. ADR-0014 D1 bans claiming the goods are certified authentic on every channel, so the page describes what the app lets a buyer *do* — zoom every image, read the attributes we publish — instead of what we vouch for. (The copy deliberately says "ข้อมูลที่เรามี", **not** "ทั้งหมด": `reference_url` is withheld by ADR-0014 D6 until OD-3 closes and `needs_review` by ADR-0009 D6, so an absolute disclosure claim would be false — don't put the word back.) The icon itself stays (on its own it reads as a question mark in a dashed circle, not an external certification mark). **Don't "fix" this page back towards the design file**, and don't add copy here that describes our inspection process either — that layer is still blocked by ADR-0014 OD-2 pending legal review.
- `test/features/onboarding/onboarding_no_authenticity_claim_test.dart` enforces the above on every CI run, over `AppStrings` *and* the rendered widget tree. Adding a new `onboarding*` constant means adding it to that test's `_onboardingCopy` list — Dart has no reflection to enumerate the class.
- The centrepiece asset on page 2 is `AppImages.questionMarkDashedCircleIcon`. It is named after the artwork rather than the caption it used to sit under, for the same reason the caption is gone (BL-74) — the rationale is on the constant itself, don't restate it at call sites.
- **The rest of this feature's tests render at 800×600, which is wider than any phone.** `test/features/onboarding/onboarding_small_screen_test.dart` is the one that renders at widths that can fail, and it asserts geometry directly as well as catching exceptions, because a text run painted past its own box raises nothing. Sizes and the text-scale axis come from ADR-0023 D5; what this kind of test can and cannot prove is in `test-quality` §5 — a real 320 dp device check is still required before SCR-01's overflow gap can be called closed.
